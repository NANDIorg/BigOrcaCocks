# Переход к разработке вдвоём

Срез до внедрения Git Flow: 25 сентября 2026, `d0b1cdc`, тег `v0.0.6`.

## Как устроен проект

Это pnpm-монорепозиторий, три пакета без отдельного сервера:

| Каталог | Ответственность |
| --- | --- |
| `apps/desktop/src/main` | Electron, процессы агентов через node-pty, Git, сокет, сохранение состояния, исполнитель воркфлоу |
| `apps/desktop/src/preload` и `shared` | Мост и типизированный IPC между main и renderer |
| `apps/desktop/src/renderer` | React, канбан, терминалы xterm.js, настройки и документация |
| `packages/core/src` | Модель, store, миграции, графы задач, правила переходов и промпты; TypeScript без отдельной сборки |
| `packages/cli/bin` | Самостоятельный JS-клиент JSON-RPC к сокету; запускается в том числе Node из Electron |
| `skills/` | Встроенные инструкции продукта для координатора, воркера и ассистента любого проекта пользователя |
| `docs/` | Архитектура, контракты задач и запросов, расследования и исторические проверки |

Состояние хранится в JSON в пользовательском каталоге приложения, не в SQLite и не в Git.
Доски двух разработчиков не синхронизируются. Общие артефакты команды — Git, PR и Issues.
Тесты используют `node:test`; desktop дополнительно использует TypeScript loader.

## Где живут инструкции

- `AGENTS.md` — вход для Codex и других агентов, раньше только ссылка на `CLAUDE.md`.
- `CLAUDE.md` — обязательные инженерные правила; прочитан целиком. До перехода предписывал
  только `orca/<taskId>` и локальный мерж приложением, что не покрывает второго разработчика.
- `skills/coordinator.md`, `worker.md`, `assistant.md` — служебные роли **продукта**.
  Их нельзя превращать в инструкции Git Flow этого репозитория: они вшиваются в приложение
  и действуют у всех пользователей. Ассистент работает только через CLI, координатор поручает
  код воркерам; эти инструкции не делают обычную сессию Codex координатором Orca.
- Правила типа задачи и системные промпты ролей живут в локальном `projects.json`.
  Они не попадают к коллеге через clone. Командный процесс должен быть в репозитории.
- Редактор «О проекте → Правила» пишет корневые `AGENTS.md` / `CLAUDE.md` открытого проекта
  (`main/rules.ts`), но не коммитит. В Git Flow открывать нужно рабочую ветку фичи.
- `docs/workflow.md` описывает граф **внутри приложения**, а не процесс выпуска этого репозитория.
- Вложенных `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, правил Cursor/Copilot и CI до перехода не было.
  `review/*.md`, QA-отчёты и `docs/investigations/*` — исторические материалы, не новые правила.

## Что мешало командной работе

1. На origin только `master`, он же default branch; защита выключена, rulesets отсутствуют.
   Разрешены merge, squash и rebase. Проверки существовали только как локальные команды.
2. `worker.ts` создаёт `orca/<taskId>` от текущего HEAD открытого проекта.
   `git.ts:mergeBranch` сливает в **текущую** ветку этого же каталога; базовая ветка
   не закреплена в задаче. Переключение этого каталога во время работы меняет цель мержа.
3. Orca не создаёт GitHub PR, не ждёт CI и второго разработчика. «Сделано» на доске
   означает завершение локального графа, а не слияние или публикацию на GitHub.
4. `commitWorktree` автоматически коммитит все оставшиеся файлы от `orca-board`, а затем
   удаляет worktree и локальную ветку. Воркеры должны сами проверять diff и коммитить
   точные файлы до сдачи; авто-коммит не заменяет проверки.
5. Node 24 был указан только в README, версия pnpm не закреплена. В README остались
   предложения про SQLite, «план» структуры и устаревшее местоположение настроек ролей.

## Принятое устройство

Полный контракт — [Git Flow](git-flow.md). Обычный агент ведёт `feature/*` и PR в `develop`.
Orca открывает отдельный worktree фичи как проект и сливает свои локальные `orca/*` в него;
владелец фичи затем готовит один PR. Два разработчика используют отдельные clone, а внутри
каждого clone — worktree на задачу. GitHub обеспечивает общую очередь интеграции.

В репозитории добавлены инструкции, CI, проверка направлений PR и версий, шаблоны задач/PR,
сборка черновика релиза по тегу и импортируемые настройки защиты. Это не добавляет
GitHub-интеграцию в сам продукт и не меняет его поведение для сторонних проектов.

## Граница внедрения

Настройки в `.github/rulesets/` — конфигурация для применения владельцем, не свидетельство,
что защита уже включена. На момент аудита текущий аккаунт имеет `push`, но не `admin`.
Порядок активации и проверка фактического состояния — в конце [Git Flow](git-flow.md).
