# Git Flow для двух разработчиков и агентов

Это обязательный процесс разработки **этого репозитория**. Инженерные ограничения —
[CLAUDE.md](../CLAUDE.md), устройство приложения — [architecture.md](architecture.md),
результат исходного аудита — [development-audit.md](development-audit.md).

## Ветки и ответственность

| Ветка | Откуда создаётся | Куда попадает через PR | Назначение |
| --- | --- | --- | --- |
| `master` | Существующая история | — | Выпущенное состояние; тег `vX.Y.Z` ставится на проверенный коммит этой ветки |
| `develop` | Однократно от `master` | Только через `release/X.Y.Z` в `master` | Интеграция следующего выпуска; default branch на GitHub |
| `feature/<issue>-<slug>` | `origin/develop` | `develop` | Фича, обычный баг, рефакторинг, документация, инфраструктура |
| `release/X.Y.Z` | `origin/develop` | `master` | Заморозка состава и стабилизация версии |
| `hotfix/X.Y.Z` | `origin/master` | `master` | Срочное исправление выпущенной версии |
| `fix/<issue>-<slug>` | Нужная `origin/release/*` или `origin/hotfix/*` | Та же ветка подготовки | Отдельная задача стабилизации через PR |
| `sync/<version>-<target>` | `origin/master` после релизного мержа | `develop` и, если есть, активная `release/*` | Перенос выпущенных исправлений и истории обратно |
| `orca/<taskId>` | HEAD проекта, открытого в Orca | Локально в ветку владельца | Служебная подзадача приложения; не самостоятельная ветка Git Flow |

Сохраняем имя `master`, чтобы не переписывать историю и существующие ссылки.
Расширение `git-flow` устанавливать не нужно: обычных Git и GitHub CLI достаточно.
В именах — латиница, цифры, дефисы; номер Issue необязателен. Не используй имя коллеги
как единственное описание ветки. Одновременно держим не больше одной активной release-ветки.

Каждая задача и каждый релиз имеют одного владельца из двух разработчиков. Владелец
отвечает за агентов, интеграцию, PR, CI и итоговую проверку. Второй разработчик ревьюит PR.
Агент действует под учётной записью своего владельца: отдельный запуск модели не является
одобрением коллеги. Не передавайте друг другу GitHub-токены.

## Начало обычной задачи

У каждого разработчика собственный clone. Один рабочий каталог — один пишущий агент;
разные задачи — разные worktree. Не переключай ветку каталога, в котором работает
другой агент, dev-сервер или Orca. Уже назначенный worktree используй как есть.

Из своего clone (пример для задачи 42):

```sh
git status --short --branch
git worktree list
git fetch origin --prune
git worktree add -b feature/42-search ../orca-42-search origin/develop
cd ../orca-42-search
pnpm install --frozen-lockfile
```

Для работы нужны Node 24 (`.nvmrc`), pnpm 10.33.0 (`packageManager`), Git и `gh`.
Установка pnpm при необходимости: `npm install --global pnpm@10.33.0`.
Работай от актуального `origin/develop`, а не от оставшейся локальной ветки.
Чужие незакоммиченные изменения не переноси и не убирай. Если исходный каталог грязный,
создай чистый worktree от remote ref: чужая работа остаётся в исходном каталоге.

До реализации прочитай `AGENTS.md` и все документы из него. В Issue или PR зафиксируй
цель, критерии готовности, владельца, границы и зависимости. Для небольшой задачи
достаточно описания PR; создание Issue не обязательный блокирующий шаг.

## Что агент делает самостоятельно

В рамках порученной задачи агент исследует проект, создаёт рабочую ветку/worktree,
меняет код, тесты и документацию, исправляет свои ошибки, выполняет проверки,
коммитит, пушит **свою** ветку и открывает/обновляет PR. Обычные шаги не требуют
отдельного подтверждения. Если PR ещё не готов — Draft с явным списком оставшегося.

Перед каждым коммитом смотри `git diff` и `git diff --cached`, добавляй конкретные
файлы вместо безусловного `git add -A`. Один логический шаг — один коммит с кодом,
тестами и соответствующей документацией. Коммиты — Conventional Commits на русском.
Конфликты разрешай в своей ветке; если меняется смысл чужой функции, обсуди с её владельцем.

Проверка перед сдачей:

```sh
pnpm verify
git diff --check
git status --short
git push --set-upstream origin feature/42-search
gh pr create --base develop --head feature/42-search --title 'feat(renderer): поиск задач' --body-file /tmp/orca-pr.md
```

Путь для `--body-file` — существующий файл с описанием по шаблону
[pull_request_template.md](../.github/pull_request_template.md); на Windows используй свою
временную папку. Автоматические строки Git/CI могут быть на английском; описания — на русском.
Состав `verify`: согласованность версий, typecheck, тесты скриптов и всех пакетов, сборка.
UI проверяется отдельно в `pnpm dev`; не утверждай, что смотрел его, если не запускал.

Для обновления фичи перед ревью:

```sh
git fetch origin --prune
git merge origin/develop
pnpm verify
git push
```

Обновлять базу можно только при чистом worktree. После разрешения конфликта проверь
весь результат, а не только конфликтовавшие строки. Не применяй `rebase`, force-push,
amend опубликованных коммитов, общий нетегированный stash или команды очистки правок.
Временную работу сохраняй WIP-коммитом в своей ветке и доводи до готовности следующими коммитами.

## PR и интеграция

- PR всегда имеет явную базу из таблицы. `feature/* → master`, `develop → master`
  и `orca/* → develop` запрещены. Нельзя назвать новую фичу `sync/*` для обхода релиза.
- CI запускается на push рабочих веток и на PR; обязательные статусы — `git-flow` и
  `quality`. `quality` ждёт typecheck, тесты и сборку на Linux, macOS и Windows.
  Нет пропуска проверок по путям файлов: документация тоже проходит контракт CLI.
- CI ставит зависимости с `--ignore-scripts` и отдельно пересобирает `node-pty` под Node
  runner (на Linux в пакете нет готового бинарника). Сокет-тесты импортируют PTY-модуль,
  но CI не проверяет интерактивный терминал и GUI. Установка для разработки и упаковка
  релиза выполняют полный набор разрешённых install-скриптов.
  На время проверок CI задаёт Git identity, `core.autocrlf=false` и сбрасывает унаследованный
  `safe.directory=*`: Git-фикстуры проверяют реальные конфликты и недоверенный каталог,
  а не случайные настройки машины runner. Настройки Git разработчика не меняются.
- Второй разработчик проверяет diff, поведение, критерии задачи и CI; нужен один approval,
  все обсуждения закрыты. Новые коммиты сбрасывают прежнее одобрение.
- Слияние — **Create a merge commit**. Squash/rebase не используем, чтобы сохранять
  историю feature, release и hotfix. Не включаем linear history и merge queue.
- В общие ветки (`master`, `develop`, `release/*`, `hotfix/*`) изменения идут только через
  PR. Создание release/hotfix от правильной базы допустимо; последующие исправления — `fix/*`.
- Сливает ответственный разработчик. Агент может выполнить мерж, только если это уже
  явно поручено и сервер подтверждает approval, свежий CI и актуальность базы. Не использовать
  admin bypass. Готовый PR без разрешения на мерж — корректная точка передачи человеку.
- После PR удали свою feature/fix-ветку и worktree только когда нет активных агентов,
  незакоммиченных изменений и коммитов, отсутствующих в целевой ветке. Используй обычный
  `git worktree remove` и `git branch -d`; не `--force` / `-D`.

Правило направления PR проверяет имена веток и версии, а не смысл кода и происхождение
каждого коммита. Reviewer всё равно проверяет базу и состав diff.

## Работа через Orca

Orca создаёт `orca/<taskId>` от текущего HEAD открытого проекта и локально сливает
их обратно в **текущую ветку того же каталога**. У приложения нет PR/CI-интеграции, поэтому:

1. Владелец создаёт worktree `feature/*` по инструкции выше. Для стабилизации — `fix/*`.
2. Добавляет **этот worktree** в Orca как отдельный проект. `projects.add` использует
   `git rev-parse --show-toplevel`, поэтому linked worktree получает отдельный root.
   Не запускает координатора на каталоге `master`, `develop`, `release/*` или `hotfix/*`.
3. Перед запуском проверяет ветку этого root и не переключает её до окончания всех
   воркеров/проверок. Одна цель фичи — один такой проект и один владелец интеграции.
4. Воркеры с `ORCA_DISPATCH_ID` сохраняют назначенную `orca/*`, сами коммитят результат
   и сдают `orca-board done`. Не создают внешние PR, не переименовывают служебные ветки
   и не трогают root проекта. Приложение выполняет локальные проверки и мерж в фичу.
5. После завершения всех подзадач владелец/обычная сессия агента проверяет **всю фичу**,
   пушит её и открывает PR. Координатор Orca следует своей роли и не становится GitHub-ботом.
6. «Сделано» в Orca означает локальную готовность. «Влито» — PR merged; «выпущено» —
   опубликованный GitHub Release после проверки установщиков.

Не публикуй служебные `orca/*` и не запускай одинаковую задачу из общей папки на двух машинах.
Доска и настройки приложения локальные; обмен задачами команды происходит через GitHub.
Редактирование правил в UI тоже делай в проекте-фиче и сдавай через PR.
Не меняй `skills/*.md` ради Git Flow этого репозитория: они вшиваются в продукт и работают
в любых репозиториях пользователей.

## Релиз

Поручения «собери релиз» / «собери и опубликуй» агент выполняет по
[docs/releasing.md](releasing.md): там описаны полномочия, release notes, сборки,
контрольные суммы, публикация и возобновление незавершённого выпуска.

Релиз — отдельное поручение, а не побочный эффект готовности фичи. До него проверь,
что `develop` зелёный и содержит согласованный набор PR. Назначь владельца и версию.
Пример ниже — **пример будущей версии**, не команда выпустить её прямо сейчас.

1. Создай и опубликуй `release/1.0.1` от актуального `origin/develop` без новых коммитов.
   Новые фичи продолжают идти в `develop`; не подмешивай их в release.
2. Создай `fix/prepare-1.0.1` от `origin/release/1.0.1`. Измени версии **одновременно**
   в корневом `package.json` и `apps/desktop/package.json`, создай описание
   `docs/releases/v1.0.1.md`. Версии внутренних core/cli
   не равны версии приложения и не требуют синхронного изменения.
3. Коммит версии — `chore: release v1.0.1`; PR в `release/1.0.1`. Ветки `fix/*`
   для дальнейших исправлений тоже идут в release с approval и CI.
4. Открой PR `release/1.0.1 → master` со списком изменений и проверок. Проверь, что версия
   больше последней выпущенной, тег свободен, root и desktop совпадают. Получи approval
   второго разработчика и зелёный CI, слей merge commit.
5. После fetch поставь **аннотированный тег именно на merge commit этого PR**, не на
   HEAD старого worktree и не на `develop`:

   ```sh
   git fetch origin --prune --tags
   gh pr view <номер-PR-релиза> --json state,mergeCommit
   git show <SHA-merge-коммита>:package.json
   git tag -a v1.0.1 <SHA-merge-коммита> -m 'Релиз v1.0.1'
   git push origin refs/tags/v1.0.1
   ```

6. `release.yml` проверяет тег/версию и присутствие коммита в `origin/master`, выполняет
   проверки, собирает macOS dmg/zip (arm64/x64), Windows NSIS/portable, манифесты и
   blockmap-файлы автообновления. Создаёт **Draft Release** с подготовленным описанием,
   `RELEASE_NOTES.md` и `SHA256SUMS`, проверяет загруженные ассеты.
   Право записи есть только у job создания черновика. Готовый релиз не перезаписывается.
7. Скачай установщики из черновика. Проверь запуск, создание проекта, старт агента/PTY,
   CLI, завершение задачи и перезапуск на заявленных платформах. Укажи непроверенные
   платформы; автоматическая сборка не заменяет живую проверку.
8. Допиши результаты проверок в release notes. Поручение «собери» заканчивается
   черновиком; «собери и опубликуй» также разрешает публикацию после проверок.
   Нет сертификатов: macOS остаётся ad-hoc, Windows — без подписи.
9. Сразу после мержа в master выполни обратную синхронизацию в `develop` (ниже),
   даже если публикация черновика отложена. Release-ветка сохраняется
   до завершения синхронизации; защищённые ветки автоматически не удаляются.

Ошибка сборки после тега: инфраструктурную временную ошибку можно перезапустить на том же
SHA. Если нужно менять код — новый patch-релиз/hotfix и новый тег. Опубликованный тег не
передвигать и не удалять. Черновики со сломанной сборкой не публиковать.

## Hotfix и обратная синхронизация

Hotfix создаётся от **`origin/master`**, а не от `develop`: иначе в срочный выпуск попадут
неготовые фичи. Опубликуй `hotfix/X.Y.Z`, затем сделай исправление и bump версии через
`fix/<slug> → hotfix/X.Y.Z`. PR `hotfix/X.Y.Z → master`, тег и черновик выпуска проходят
тот же порядок проверок, что релиз. Срочность не отменяет approval коллеги и CI.

После любого release/hotfix сохрани историю финального master merge в следующих ветках:

```sh
git fetch origin --prune
git worktree add -b sync/1.0.1-develop ../orca-sync-1.0.1 origin/master
cd ../orca-sync-1.0.1
git merge origin/develop
pnpm verify
git push --set-upstream origin sync/1.0.1-develop
gh pr create --base develop --head sync/1.0.1-develop --title 'chore: перенести релиз 1.0.1 в develop' --body-file /tmp/orca-sync-pr.md
```

Это PR-перенос merge-истории, не cherry-pick. Если после hotfix уже есть активная
`release/1.1.0`, сделай **второй** `sync/*` от `origin/master`, в нём слей именно эту
release-ветку и открой PR в неё. Не вливай `develop` в release. При конфликте версий
сохраняй более высокую версию целевой release-ветки в обоих package.json; не откатывай
её до номера hotfix. Нельзя закрывать релизную задачу до обоих переносов.

## Откат

Не переписывай историю общей ветки. Ошибочная фича в `develop` отменяется отдельной
`feature/revert-<номер>` с `git revert -m 1 <merge-SHA>` и PR в `develop`.
Ошибка в выпущенном приложении исправляется через hotfix: revert в `fix/*`, новая patch-версия,
новый релиз и перенос обратно. Перед revert проверь зависимые изменения и тесты.

## Однократное включение на GitHub

Созданные файлы CI и rulesets сами по себе **не включают защиту**. Владелец с `admin`
должен выполнить настройку после первого зелёного PR внедрения.

1. Создать `develop` от текущего `master`, если её ещё нет; первый PR `feature/git-flow`
   направить в `develop`. Если master успел продвинуться за время внедрения, перенести
   его актуальную историю в этот первый PR merge-коммитом, сохранив новые правила
   проекта и изменения продукта. Слить после ревью и зелёных `git-flow` / `quality`.
2. В Settings → General поставить default branch `develop`; оставить только merge commits,
   выключить squash/rebase и автоудаление веток (release/hotfix нужны до переноса обратно).
3. Импортировать `.github/rulesets/git-flow.json` и `release-tags.json` через
   Settings → Rules → Rulesets → Import a ruleset. Правила активные, без обхода администратора:
   один approval, сброс approval при новых коммитах, последнее изменение одобряет другой
   участник, закрытые обсуждения, актуальная база, `git-flow` и `quality`, запрет удаления
   и force push общих веток; запрет изменения/удаления `v*` тегов.
4. Если удобнее API, из актуального worktree владелец выполняет:

   ```sh
   gh api --method PATCH repos/NANDIorg/BigOrcaCocks -f default_branch=develop -F allow_merge_commit=true -F allow_squash_merge=false -F allow_rebase_merge=false -F delete_branch_on_merge=false
   gh api --method POST repos/NANDIorg/BigOrcaCocks/rulesets --input .github/rulesets/git-flow.json
   gh api --method POST repos/NANDIorg/BigOrcaCocks/rulesets --input .github/rulesets/release-tags.json
   ```

   POST создаёт правила, не обновляет: перед повтором посмотри существующие rulesets;
   обновление — PUT по их id. Не создавай дубликаты. Для очистки завершённой защищённой
   release/hotfix-ветки владелец отдельно меняет правило после проверки обратного переноса;
   обычный агент не обходит запрет удаления.
5. Убедиться, что GitHub Actions разрешены. PR-workflow использует `contents: read`;
   `contents: write` нужен только созданию Draft Release. Секреты Apple/Windows для текущей
   ad-hoc/неподписанной сборки не требуются.
6. Проверить фактическое состояние: `gh api repos/NANDIorg/BigOrcaCocks/rulesets` и настройки
   default branch. На тестовом PR убедиться, что без approval/CI кнопка мержа заблокирована.
7. Оба разработчика обновляют clone и читают новые правила. Первый следующий релиз
   принесёт эти файлы в `master`; существующие теги, включая `v1.0.0`, не пересоздаются.

Первый PR внедрения — единственное исключение: новые проверки уже запускаются из него,
а серверную защиту включают после его слияния. Не объявляй процесс полностью защищённым,
пока правила не применены владельцем.

Документация GitHub: [защищённые ветки](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches),
[API rulesets](https://docs.github.com/en/rest/repos/rules),
[права GITHUB_TOKEN](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).
