# Выпуск релиза по поручению человеку или агенту

Это инструкция для разработки **orca-board**, а не для агентов продукта в чужих проектах.
Перед выпуском прочитай [Git Flow](git-flow.md); устройство пакетов и автообновления —
[architecture.md, «Сборка»](architecture.md#сборка). `master` — релизы и hotfix;
обычные задачи идут через `feature/* → develop`.

## Что означает поручение

| Поручение | Результат |
| --- | --- |
| «Собери релиз 1.1.0 с описанием и сборками» | Релизные PR, версия, аннотированный тег, зелёный Release workflow, заполненный **черновик** GitHub Release со всеми файлами, обратный sync-PR |
| «Собери и опубликуй релиз 1.1.0» | То же плюс публикация после проверок; отдельное повторное разрешение на публикацию не требуется |
| «Опубликуй подготовленный релиз 1.1.0» | Проверка существующего тега, CI, описания, файлов и результатов smoke-проверки, затем публикация существующего черновика |
| «Подготовь PR релиза 1.1.0 без мержа» | Подготовленные PR; тег и публикация не выполняются |

Обычное поручение собрать выпуск разрешает агенту подготовку, коммиты, push, PR,
слияние одобренных PR, тег и создание черновика. Оно **не отменяет** обязательное
одобрение второго разработчика, свежий CI и разрешённые направления PR.
Если approval ещё нет, доведи PR до готовности и дай ссылку с указанием, чьё действие
нужно; не запрашивай заново уже данное разрешение владельца и не обходи защиту.
Агент-ревьюер под тем же GitHub-аккаунтом не заменяет второго разработчика.

Это работа агента в текущей сессии и Actions после push тега. Фоновый бот, который
сам начинает следующий релиз или ждёт ревью после окончания сессии, не устанавливается.

## 1. Проверить исходное состояние

- Fetch веток и тегов; проверь открытые release/hotfix/sync PR, существующие черновики,
  опубликованные версии и уже выполняющиеся Release workflow. Продолжай подходящий
  незавершённый выпуск, не создавай второй черновик или параллельный релиз.
- Сверь `origin/master`, `origin/develop` и последний опубликованный тег. Если `master`
  ещё не перенесён в `develop`, сначала доведи соответствующий sync-PR до слияния.
  Состав обычного релиза — согласованные изменения `develop`; hotfix — только от `master`.
- Если версия не указана: исправления — patch, совместимая функциональность — minor,
  несовместимые изменения — major. Назови выбранную версию и причину до изменений.
  При неоднозначной совместимости уточни только этот вопрос. Номер должен быть больше
  опубликованных версий; существующие теги не переиспользуй. Поддерживается `X.Y.Z`,
  без prerelease/build suffix; beta-канал — отдельная задача.
- Работай в отдельном worktree. Не переключай открытый проект с живыми воркерами Orca.

## 2. Подготовить версию и описание в PR

Следуй последовательности `release/X.Y.Z` от develop → `fix/prepare-X.Y.Z` → PR в release.
Для hotfix аналогично, исходная ветка — master. В fix-ветке:

1. Обнови `/package.json` и `apps/desktop/package.json` одним коммитом
   `chore: release vX.Y.Z`. Версии внутренних core/cli не меняются вместе с приложением.
2. Создай **`docs/releases/vX.Y.Z.md`**. Это проверяемый в PR источник release notes,
   который CI переносит в описание и файл `RELEASE_NOTES.md` GitHub Release.
3. Собери содержание из реального diff, истории коммитов и вошедших PR с прошлого
   опубликованного тега до release-ветки. Описание — на русском, для пользователя:
   новые возможности, исправления, изменения совместимости и данных, шаги обновления,
   известные ограничения. Добавь ссылки на PR и сравнение тегов. Не выдавай планы
   за сделанное; пустые разделы и служебные merge-коммиты перечислять не нужно.
4. Укажи сборки: macOS arm64/x64, Windows x64 NSIS/portable. Отрази текущие ограничения:
   macOS ad-hoc без нотаризации, Windows без подписи; реальные результаты ручных
   проверок записывай после их выполнения. Не заявляй поддержку Linux-сборки.
5. Выполни `pnpm verify`, открой PR с версией, составом выпуска и проверками.
   После approval и CI слей подготовку в release, затем release в master merge-коммитами.
   Последующие изменения требуют нового approval. По возможности дождись всех
   результатов ревью в сессии; если нужно действие коллеги — передай готовый PR.

Пример структуры notes (заполняется фактами конкретного выпуска):

```markdown
# orca-board X.Y.Z

Кратко: что изменится для пользователя.

## Новое
- Возможность и её применение. Ссылка на PR.

## Исправления
- Какой сценарий теперь работает правильно. Ссылка на PR.

## Обновление и ограничения
Миграции, установка, известные ограничения и ссылки на инструкции.

Полный список изменений: ссылка на compare предыдущего и нового тегов.
```

## 3. Тег и автоматическая сборка

Получив **merge SHA релизного PR** через `gh pr view <номер> --json state,mergeCommit`,
проверь состояние MERGED, версии на этом SHA и его присутствие в `origin/master`.
Поставь `git tag -a vX.Y.Z <merge-SHA> -m 'Релиз vX.Y.Z'`, затем
`git push origin refs/tags/vX.Y.Z`. Не ставь тег на HEAD рабочего каталога по привычке.
Если тег уже существует, проверь точное совпадение SHA и продолжи существующий workflow.

`.github/workflows/release.yml` запускается только по тегу:

1. Проверяет тег, обе версии, master и непустое описание `docs/releases/vX.Y.Z.md`.
2. Ставит зависимости, выполняет `pnpm verify` и упаковывает приложение на macOS/Windows.
   Обе mac-архитектуры строятся одной job, чтобы `latest-mac.yml` включал обе.
   Проверяет `codesign --verify --deep --strict` для обоих `.app`.
3. Передаёт сборки отдельной job. У упаковщиков только `contents: read`, публикация
   electron-builder выключена. Только job `draft` имеет право записи в GitHub Releases.
4. Проверяет непустые обязательные файлы, версии и ссылки в манифестах, создаёт
   `SHA256SUMS`, загружает описание и файлы в единственный черновик. Проверяет через
   GitHub API имена, размеры и состояние загруженных ассетов.

Обязательный комплект:

| Файлы | Назначение |
| --- | --- |
| `orca-board-X.Y.Z-arm64.dmg`, `orca-board-X.Y.Z-x64.dmg` | Установка macOS |
| `orca-board-X.Y.Z-arm64.zip`, `orca-board-X.Y.Z-x64.zip`, их `.blockmap` | Автообновление macOS |
| `orca-board-X.Y.Z-x64.exe` и `.exe.blockmap` | Установка и автообновление Windows NSIS |
| `orca-board-X.Y.Z-portable-x64.exe` | Windows portable |
| `latest-mac.yml`, `latest.yml` | Манифесты автообновления; имена файлов менять нельзя |
| `RELEASE_NOTES.md`, `SHA256SUMS` | Описание выпуска и SHA-256 всех приложенных файлов, кроме самого SHA256SUMS |

Отдельные `.dmg.blockmap`, если их создал упаковщик, тоже прикрепляются и входят в суммы.
Архивы исходников GitHub добавляет сам. Другие файлы (например, инструкция миграции)
прикладывай по поручению пользователя: проверь содержимое, загрузи конкретные пути,
дополни SHA256SUMS и проверь скачивание. Не прикладывай весь рабочий каталог.

## 4. Проверить и при необходимости опубликовать

- Найди запуск по **тегу и SHA** (`gh run list --workflow release.yml`), дождись его
  успешного завершения (`gh run watch <id> --exit-status`). Красный workflow — неготовый
  релиз, даже если черновик уже виден. Результаты CI из другой ветки не подходят.
- Скачай ассеты из черновика (`gh release download vX.Y.Z --dir <новая-папка>`),
  проверь `sha256sum --check SHA256SUMS` (macOS: `shasum -a 256 -c SHA256SUMS`).
  Сверь описание, комплект, версии манифестов и присутствие обеих архитектур macOS.
- Smoke-проверка скачанных сборок до публикации: запуск, проект, агент/PTY, CLI,
  задача и перезапуск. Проверь подписи и манифесты. Черновик невидим приложениям,
  поэтому сквозное автообновление с предыдущей версии здесь ещё не проверяется.
  Запиши в PR и описание черновика фактически проверенные ОС/архитектуры и ограничения.
  Если платформы недоступны, явно передай этот пункт владельцу; публикация требует
  его принятия этих конкретных непроверенных сценариев, а не молчаливого пропуска.
- Если поручено только «собери», оставь черновик. Если поручено «опубликуй» и проверки
  выполнены, используй `gh release edit vX.Y.Z --draft=false --prerelease=false --latest`.
  Для более старой линии hotfix не делай её Latest поверх новой версии: сначала уточни
  целевой канал, поскольку приложение читает последний стабильный выпуск.
- Проверь API релиза (`isDraft=false`, нужный tag) и скачивание публичных
  `releases/latest/download/latest-mac.yml` и `latest.yml` с правильной версией.
  Теперь проверь автообновление с предыдущего выпуска; для portable — ручное
  скачивание нового exe. При поручении «собери» отметь эту проверку отложенной
  до публикации. Ошибка после публикации требует следующего patch/hotfix.
- После мержа в master выполни обратный перенос через `sync/* → develop` и активную
  release-ветку, если она есть. Не откладывай перенос на публикацию: черновик тоже уже
  изменил master. Approval/CI обязательны и для sync-PR.

В итоговом ответе: версия, ссылка на черновик/релиз, SHA и тег, релизный и sync-PR,
ссылка на успешный workflow, приложенные файлы и результаты/ограничения smoke-проверки.
Пока нужны review, CI или ручная проверка, называй конкретный незавершённый шаг.

## Повторный запуск и ошибки

Существующий черновик с тем же тегом можно дополнять: повторный запуск перезальёт его
файлы и описание из проверенного коммита. До перезапуска сохрани отдельно добавленные
вручную результаты проверок/дополнительные файлы и затем восстанови их с контрольными
суммами. Несколько релизов одного тега, опубликованный релиз или ошибка API прерывают
workflow; автоматического удаления нет.

Временный сбой runner/сети — повтори запуск на том же SHA. Исправление кода или workflow
после тега — новая patch-версия через release/hotfix; тег не перемещай. Уже опубликованные
бинарники и манифесты не заменяй: для исправлений выпускай следующую версию.
