## Требования пользователя

- Отдельная программа, которую можно установить командой на удалённый сервер, без установки desktop/Electron.
- Основной интерфейс — интерактивный чат в терминале, как Codex/Claude, используемый по SSH. Через разговор человек управляет оркестрацией; явные команды и slash-команды дополнительны.
- Правила, функции, роли и workflow должны совпадать с desktop. Полное покрытие desktop — продуктовая цель; первый выпуск выполняет рабочий цикл целиком из чата.
- Codex и другие агенты запускаются на самом сервере. Подключение локального desktop к удалённому серверу — последующий отдельный сценарий.

## Рекомендуемая архитектура

Один монорепозиторий, два устанавливаемых продукта и общий внутренний движок. `packages/core` сохраняет browser-safe модель; `packages/contracts` содержит общие DTO; новый `packages/runtime` получает executor workflow, проекты, persistence, Git, сессии и диалоговый сервис из desktop/main. Desktop и headless host используют один runtime. Терминальный чат — клиент общего диалога и read-only событий.

Для первой поставки — один публичный CLI npm-пакет с собранным JS, headless entrypoint, skills/prompts, совместимым agent client и native-зависимостями. Core/runtime/contracts остаются private workspace-модулями и включаются в сборку. Имя npm-пакета условное, право публикации не проверено. Платформенные архивы с включённым Node можно добавить позднее без новой реализации движка.

Пользователь открывает `orca`; клиент подключается к своему host или запускает его. Daemon владеет состоянием, диалогом и процессами агентов, поэтому разрыв SSH не прекращает работу. Отдельная установка сервера не требуется. После reconnect возвращаются transcript, статусы и ожидающие вопросы.

## Что уже есть и важно переиспользовать

- `packages/cli/bin/orca-board.js` — существующий dependency-free JS-клиент сокета. Его использует desktop и skills; сохранить формат, команды и ORCA-контекст.
- Core уже содержит доменные проверки и чистые переходы, но фактическое выполнение находится в desktop/main. Использования одного core недостаточно для самостоятельной программы.
- `skills/assistant.md` уже описывает управление доской естественным языком. `AssistantSession` и `assistant-conversation` имеют Codex app-server, Claude stream-json и ACP. Основной ассистент и structured chat transports включены в MVP.
- Рабочие агенты сначала сохраняют PTY. Перевод worker/coordinator на structured drivers — следующий проект. Provider ассистента и модели рабочих ролей выбираются отдельно.
- Общие services выполняют одинаковые guards и effects для обоих интерфейсов. Успешный текст LLM не заменяет результат tool/runtime.

## Границы, которые нельзя потерять

- Один dataDir — один owner; lock до backup/миграций/load. TaskStore при загрузке считает прежние dispatch прерванными: короткие CLI-команды не открывают store сами.
- `check` потребляет события координатора. Терминальный монитор использует отдельную read-only подписку, не меняет consumedBy.
- Disconnect/выход чата не вызывает stop агентов. Рестарт самого owner прерывает PTY; восстановление задач/worktree и живое продолжение provider conversation — разные механизмы.
- Текущий Codex transport создаёт thread/start. Для сохранённых диалогов нужен provider binding и thread/resume; повторные mutating tool calls из transcript не проигрываются.
- Provider permission/question, подтверждение действия и HumanRequest результата имеют разные request ids и правила ответа. Поздние ответы не применяются к новой сессии/turn.
- Node/Electron native ABI проверяются в разных install/build roots. Installed Linux smoke нужен с реальным PTY spawn; local monorepo tests не заменяют проверку поставляемого пакета.
- Пока сохранить JSON/migrations. SQLite, новая реализация providers, remote desktop и новый scheduler не смешиваются с извлечением runtime.

Следующее обсуждение может уточнить архитектуру или связать её с другой фичей. Этот PR хранит основу и не является поручением начать реализацию или слить PR.
